**15 November 2026 (deployed, version `a32e1471-5276-438d-a0dd-0fac41693723`):** device exchange accepts an optional `state.health` object (`resetReason`, `rssiDbm`, `wifiReconnects`, `uploadFailures`, `queuePending`, `freeHeap`, `minFreeHeap`, `largestFreeBlock`, `aht`/`bmp` `{ok,recovered,failed}`, `sd` `{state,fileBytes,flushes,flushFailures,verifyFailures,bufferedBytes,droppedRecords,lastFlushAgeSec}`). It is sanitized field by field and never rejects an exchange; invalid fields are dropped. `/api/snapshot` device views add `recentBoots` (last 8 boots with the firmware `BOOT reset=...` log line). The `*/5` cron also sends one Discord message when a device has not exchanged for `OFFLINE_ALERT_AFTER_MINUTES` (default 20, minimum 10) and one when it is back, stored as `system_state` key `offline_alert:<deviceId>`. Skipped while uploads are paused.

**18 November 2026 (deployed, version `84bbab7f-8749-4e3e-9472-c33f847a48e4`):** gas-warning alerts are configurable from the dashboard (Settings > Gas warning alerts). Settings are global (every device), stored as D1 `system_state` key `alert_settings` (`{revision, settings}`); no migration. Until saved, defaults apply (`GAS_ALERT_AFTER_MINUTES`, default 60).
- `GET /api/alerts`: `{revision, settings, savedAt, defaults, checkEveryMinutes, channels:[{id,name,connected}], serverChannelId, delivery:{lastSentAt,lastKind,lastError:{code,at,kind,message}}, variables:[{name,description}]}`.
- `PUT /api/alerts` with `{expectedRevision, settings}`: 409 `alert_settings_changed` on a stale revision, 400 `invalid_alert_settings` with the first problem. `settings`: `enabled` (bool), `channel` (`discord` only), `discordChannelId` ('' or 17–20 digits; overrides `DISCORD_CHANNEL_ID`), `afterMinutes` (5–720), `remindEveryMinutes` (0, 30, 60, 120, 180, 360, 720), `mention` (`none`/`here`/`everyone`, pings only on warning and reminder messages), `warningTemplate`, `sendEnded` (bool), `endedTemplate` (each up to 1500 characters, `{variable}` names from `public/alert-settings.js`; unknown names are rejected).
- `POST /api/alerts/test` with `{kind:'warning'|'ended', settings, deviceId?}`: sends the given (possibly unsaved) settings once, marked as a test and never pinging, using the device's latest stored reading. Failure: 502 `alert_delivery_failed` with a plain-language reason.
- Every gas message ends with a fixed line saying MQ-135 is a relative gas response, not calibrated ammonia ppm. The last delivery result (any alert kind, including offline/online and tests) is kept in `system_state` key `alert_delivery`; a repeated identical failure is written once. Offline/online messages use the chosen service and channel but never mention.

All `/api/*` routes except device exchange require the owner bearer key or a signed owner cookie. Public static assets and `/health` contain no readings. No cross-origin API access is enabled.

Audit changes deployed with explicit authorization on 12 October 2026: JSON request bodies must be objects with `application/json` (case-insensitive; charset parameters accepted). Malformed/oversized log cursors return 400. Both CSV exporters escape formula-like text, including leading whitespace and full-width formula prefixes, while preserving numeric measurement values; raw JSON/archive values are unchanged. Owner-session creation fails with 503 when its signing secret is unavailable. Login throttling is best-effort per Worker isolate, not a global rate limit. See [audit report](../../docs/BACKEND_AUDIT_2026-10-12.md).

Legacy History parameters (without `pageSize`): `deviceId` (default `coop-monitor-01`), `from`, `to` (ISO dates; maximum 31-day range), `limit` (1–60 minute blocks; default 30), `cursor` (prior `nextCursor`), `order` (`asc` by default, or `desc` for newest blocks first and pagination toward older blocks). Default range is the last hour. Follow `nextCursor` until null for a full export, keeping the range and order unchanged. CSV export retains ascending API retrieval and a 50,000-reading browser limit; use paginated API retrieval for larger ranges.

Without `pageSize`, `mode=latest` returns the newest individual readings within the recent retention period, ordered by server-anchored sample time descending. In this legacy mode `limit` is a reading count (1–100, default 100); date-range and cursor parameters are not used, and `nextCursor` is null. For example, `/api/history?deviceId=coop-monitor-01&mode=latest&limit=100`. Existing block pagination, trend requests and CSV export remain unchanged.

Adding `pageSize` opts into **individual entry pagination**, 50–1000 entries per request. `order=desc` (default) means newest first; `order=asc` means oldest first. Use `mode=latest` for the recent retention window (which can be traversed from either end) or `from`/`to` for a selected range (inclusive endpoints, maximum 31 days). `limit` is unused in this mode. Follow the opaque `nextCursor` with the same device/mode/range/order; the latest cursor freezes its original time window. Cursor ordering uses estimated time, binary boot ID and sequence, allowing a page boundary within a minute block without losing or repeating entries. Cursors bind the direction; older six-field cursors remain valid for descending requests. Candidate blocks and overlapping boot windows are bounded before JSON projection/sorting; at most `pageSize+1` tuples return from D1. No schema change or device write is involved.

Numbered pages (20 November 2026): without a `cursor`, an optional `offset` (0–2,000,000; the response echoes it) skips that many entries, so page N is `offset=(N-1)*pageSize`. Sending `offset` with a cursor returns 400 `invalid_offset`, except `offset=0`. The result equals the page reached by following cursors, including its `nextCursor`. The server does not sort the skipped entries. Minute-block sizes (`json_array_length`) locate a pivot block. One exact count follows: interior blocks are counted by size, and only the blocks next to the pivot time and the range end are counted entry by entry. A short remainder is then skipped with `OFFSET`. This relies on the existing rule that every reading lies within 60 s after its block start. A deep jump reads roughly twice the blocks between the range end and the target page; a 30-day jump costs about one selection count.

The History tab shows one page at a time; Rows per page (50, 100 default, 250, 500, 1000) sets the size, with newest/oldest first. Below the table are Previous/Next, page numbers (first, last and the pages around the current one, with gaps; 7 slots, 5 on phones) and a page box. A typed number above the last page opens the last page. Every page of a view uses one pinned window: the applied range, or for Latest the `from`/`to` that its first `mode=latest` response reported (later pages are range requests on that window). The page count comes from `/api/archives/selection`: the range count, or a count of the pinned Latest window. Without a count, the pager steps page by page. Neighbouring pages follow cursors; other pages use `offset`. Changing size, order, view or device starts again at page 1. No. counts across all pages, with 1 as the oldest reading of the view. Newest first needs the count, so the column stays blank until it arrives. Unsubmitted date-input edits do not change a running selection.

Logs: `deviceId`, optional returned `cursor`; 100 rows/page. `nextCursor` also works for incremental polling. Stored rows use snake_case SQL names. Retention is 24 hours plus bounded pruning lag. Archives catalog: 100 records/page; `nextCursor` until null.

Manual archives use ISO `from` / `to`, inclusive endpoints on the server-anchored `estimatedAt` timeline, and a maximum 31-day range. They count individual readings still in D1, excluding previously archived entries and console logs. The History date picker shares the read-only `/api/archives/selection` count: it updates after date edits, on History entry/device changes, and when loading a range. This total is separate from loaded table rows and is independent of page size/order; editing dates leaves the loaded table intact until submission. Empty/invalid selections and failed count requests are shown explicitly; stale replies cannot replace a newer selection. Counts are a point-in-time preview and can change as readings arrive or are archived. Labels are trimmed, required, and limited to 80 characters without control characters. Creation rechecks `expectedCount`; a changed count returns `409 selection_changed` for user review. The returned job includes `archive_id`, `label`, `range_from`, `range_to`, `selected_count`, `archived_count` and `status` (`running` / `complete`). Continue POSTs until complete; repeating a completed POST has no effect. There is no automatic background continuation. `/api/archives` includes the latest 100 `manualArchives` jobs on the first catalog page; chunks include their `manual_archive_id`, label and range.

Each manual chunk keeps the version-1 tuple/block format and adds `manualArchive:{id,label,from,to}`. R2 upload, full readback and SHA-256 verification precede one atomic D1 transaction that removes only selected tuples, records the verified manifest and advances progress. Outside-range tuples, device state, exchange counters and sample identity/value fingerprints remain. Identical firmware retries are acknowledged without reinsertion; changed values retain the existing `sample_conflict` response, and the 32-sample minute limit still includes archived identities. Capacity, live maintenance leases and concurrent changes can stop a chunk with a recoverable error. Committed chunks remain available; failed chunks keep their source entries. New/late readings within the range can change the eventual total from the initial count. History continues to query only unarchived readings.

Commands: `{type,args:{},ttlSec:60}`. TTL 15–300 seconds, maximum 10 active commands per device. `CAL_START` args must explicitly confirm known reference conditions. Types: `CAL_SHOW`, `CAL_EXPORT`, `CAL_START`, `CAL_CANCEL`, `NET_STATUS`, `NET_RECONNECT`, `CONFIG_SHOW`, `RESTART`, `HELP`, `SD_STATUS`, `SD_TAIL`, `SD_FLUSH`, `SD_EJECT`, `SD_MOUNT` (SD types need firmware `cloudflare-1.2.0`; the dashboard disables them for older firmware). No free-form shell, Wi-Fi credential updates, calibration import, or firmware OTA endpoint.

Errors use `{error,message}` with status 400 invalid payload, 401 missing/invalid credential, 403 cookie origin failure, 404 unknown resource, 409 reused sample values/revision conflict/full command queue, 413 body >64 KiB, 415 wrong content type, 429 owner login throttle, 503 backend/provider failure. No request bodies or credentials are emitted to Worker logs.

## Archive folders and bulk downloads

Deployed with explicit approval on 13 October 2026 as Worker `d19d670b-57b4-4108-be5f-ed7ca5b35c32`. Local browser/tests and live assets/private archive reads/download checks passed. Existing catalog/download routes remain available.

The library uses owner-only GET /api/archive-folders with deviceId and an opaque nextCursor. It groups each manual job by archive ID, including running jobs without files; duplicate labels stay distinct. Automatic chunks group by UTC day of their hour_start (folder ID `auto:YYYY-MM-DDT00:00:00.000Z`, label `Automatic archive YYYY-MM-DD (UTC)`, range one UTC day); older hourly `auto:` IDs return 400. Stored objects and manifests are unchanged. Each folder includes folder_id, type, label, range_from/range_to, archived_at, status, file_count, sample_count and compressed_bytes. Completed manual archives use the job completion timestamp; automatic archives use the latest saved-file timestamp. Folder pagination returns 50 groups ordered by archive date and ID descending, with device-bound cursors.

GET /api/archive-files takes deviceId, folder (the returned folder_id) and cursor. It returns 100 verified manifest files per page ordered by created_at/object_key; cursors bind both device and folder. Missing folders for the requested device return 404; malformed folders/cursors return 400. These routes only read existing tables; the legacy catalog, individual download route, archiving, ingestion and schema remain unchanged.

Bulk download is client-side: Download all walks every file page; Download selected uses the checked files among loaded pages. The browser fetches the existing private /api/archive files, verifies every compressed SHA-256, then puts the unchanged gzip bytes in one ZIP with unique part names. A failed read/hash produces an error and no partial ZIP. Device/logout/library reset cancels an in-progress download. Browser memory and standard ZIP limits apply to very large selections; smaller selections remain available. No new R2 object is created by downloading.
