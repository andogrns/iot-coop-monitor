# Seven-day standalone field run: 5 November 2026

The agreed run is planned to start in the coop on 5 November, with the ESP32 uploading over Wi-Fi. The present priority is preserving a complete week of data. Retain firmware `cloudflare-1.0.4`, checked sensor retries and the disabled OLED while starting collection. On 4 November afternoon the user installed a replacement AHT/BMP with power off: its 15-minute test produced 180 complete readings with zero retries/final failures and 15/15 successful BMP ID probes. Keep this replacement installed. The earlier module's first-attempt failure mechanism remains unproved, while its symptom was absent in this replacement test.

This is a launch procedure, not evidence that the week has started or that cloud delivery currently works. The actual start/end timestamps must be recorded when field readings are verified in History.

## Before leaving for the coop

1. Keep the replacement MQ powered for initial conditioning. On 4 November the user reported about 35 hours already accumulated and plans continued power through the day. That user update supersedes the earlier less-than-one-hour observation; heater-power continuity has not been independently measured.
2. After more than 48 hours of initial conditioning and stable output, obtain its own accepted clean-air profile using the documented calibration procedure: `CAL START`, ten minutes stabilization plus five minutes collection, `@CAL,SAVED`, then `CAL EXPORT`. The reference air must be confirmed separately from coop air. No calibration is started by the preflight tool. Record profile/fingerprint changes; old `mq135-01` calibration is not applicable to `mq135-02`.
3. Have stable power and the intended 2.4 GHz Wi-Fi available at the installation point. Laptop Ethernet access alone does not connect the ESP32. A login/captive-portal web page cannot be completed by the current ESP32 firmware.
4. Keep the tested USB cable/laptop available for setup and temporary capture. Nothing installs or schedules a permanent computer logger.

## Wi-Fi setup and launch

Close Serial Monitor and any other COM-port owner first. COM5 was the last observed ESP32 port on 4 November; recheck it after moving machines or reconnecting.

If the saved network is not the intended available network, run the existing provisioning helper in PowerShell:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ./firmware/coop_monitor/configure_network.ps1 -Port COM5
```

It prompts locally for the 2.4 GHz SSID and secure password and uses the existing private device configuration. Do not put Wi-Fi passwords/device tokens into reports or checked-in files. Provisioning changes saved settings; it is distinct from the read-only preflight below. No provisioning was performed during the 4 November preparation unless recorded in its verification report.

Run the bounded 15-minute preflight while connected to the **actual field network**:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File ./firmware/coop_monitor/preflight_field_run.ps1 -Port COM5 -DurationSeconds 900 -ReconnectOnce
```

The tool saves all complete readings and diagnostics under ignored `outputs/field-preflight/<UTC timestamp>/`, closes the Serial port, and writes `result.json`. It never flashes, calibrates, imports a profile or changes stored settings. `-ReconnectOnce` requests one reconnect using the saved settings; omit it for strictly observational checking.

The device-side requirements are:

- `acquisition_pass: true`: fresh complete AHT/BMP samples, expected module identity, no invalid samples, sequence gaps, resets or final sensor failures during the check. Recovered attempts remain explicitly reported.
- `device_cloud_path_pass: true`: repeated fresh accepted HTTPS protocol responses, synchronized clock, bounded queue and stable recent drop count. A Wi-Fi connection or HTTP 200 alone cannot pass.
- At least one MQ diagnostic with no zero/full-scale/high-ADC event. Missing calibration remains a separate raw-only limitation rather than being silently accepted as calibrated research data.

Then verify **actual new persisted History rows** on [Coop Monitor](https://coop-monitor-worker.coop-monitor-worker.workers.dev/), selected device `coop-monitor-01`. Confirm the last-reading time and sample sequence advance, desired/applied settings agree, uploads are enabled and there is no capacity pause. Device preflight deliberately does not claim this independent backend readback.

After transfer to the intended standalone power source, verify fresh History rows again. The source may reboot during transfer; record the new boot and wait for readings/clock/uploads to resume. Start the seven-day field window from the first verified reading under the final placement and power setup, not from today's bench check. The OLED is disabled and was intentionally disconnected in the 4 November closed-lid test; use the dashboard for readout.

The normal firmware samples and uploads automatically; a separate week-start command is unnecessary. Define the week with a recorded start/end window. Exclude earlier bench/transport backlog from that window and preserve timestamp-quality information: records collected before clock synchronization can retain an unknown device timestamp and a separately estimated timestamp. Do not silently relabel those as precisely timed field readings.

## Protecting the week of data

- At the last verified five-second interval, nominal coverage is 17,280 readings/day and 120,960/seven days. Use the actually applied interval when evaluating completeness. Recheck interval/revision after connecting, since the cloud may apply desired settings.
- Only 64 readings fit in RAM: about 320 seconds at five-second sampling. Longer network outages drop old records; power loss discards pending RAM. There is no active SD/flash measurement recorder in this build. A one-week collection therefore depends on working Wi-Fi/uploads and stable power.
- Check fresh History rows, boot changes, gaps, status flags and drop counts at least daily. Export a daily copy; browser History export splits larger exports into 50,000-row parts. Keep every part and confirm the exported coverage, rather than relying on the page showing only a recent subset.
- Record power/network interruptions, installation changes and calibration changes with timestamps. Keep failed/missing/uncalibrated rows with quality flags; do not silently smooth gaps or relabel raw MQ voltage as ammonia ppm.
- Keep the 5 November dataset identified as replacement module `mq135-02`. Raw MQ voltages from different physical modules are not automatically comparable to the prior damaged sensor's readings.
